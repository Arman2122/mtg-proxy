# shared with a database; load 0.1-0.7 at the start of each session, other tenants logged in), from /root/mtg-bench:
#   new = commit 91eb7fb (the final CODE of piece B; every later commit is documentation)
#   old = commit 4024026 production (before any per-address code on the data path) + the final mtglib/door_bench_test.go
#         (the file compiles against both trees; it is copied by name)
#   hs  = commit c695b6a, the tip of piece A (handshake at scale), which piece B is stacked on
# Protocol: alternating process runs, the order swapped every iteration, `-test.cpu 2 -test.benchtime 1s`, TIME_WAIT < 200
#   between runs, benchstat default settings (alpha 0.05):
#   1. wrapper noentry rows        '^BenchmarkCountingConn(Parallel)?$/^(read|write)$/^noentry$'          old vs new, 10 iterations
#   2. door bulk rows              '^BenchmarkDoorBulk$'  (9 rows + the 9 `/tracked` twins)                old vs new, 10 iterations
#   3. handshake rows              '^BenchmarkDoorHandshake$/^(ee-unpaced|dd)$/^(secrets=1|secrets=1000)$' and
#                                  '^BenchmarkDoorHandshake$/^ee-unpaced$/^secrets=5000$/^last$/^hinted$'   hs vs new, 8 iterations
#   4. a focused re-check of the one wrapper row that looked slower (below), 15 iterations x 2 samples = 30 per side
#   5. informational, new binary only: wrapper rows with an entry, a ceiling, a fair limiter; door rows with the controls on
#      (3 samples: benchstat gives no interval); BenchmarkFairTick (3 samples)
#
# RESULT (read before the tables)
#  * Data path, 18 door bulk rows (untracked and tracked): no row differs (all p > 0.05), geomean +0.03% in time.
#  * Handshake rows against piece A's tip, 11 rows: no row differs (all p > 0.05), geomean +0.94%. The two nearest to the line are the ee
#    hinted secrets=1000 row (+8.3%, p = 0.083, noise +-7-8%) and the ee last secrets=1000 row (-6.2%, p = 0.065).
#  * Wrapper `noentry` rows (a stream with no per-address entry: tracking off and no control, i.e. the old code plus one atomic load):
#    three of four rows show no difference. `CountingConnParallel/read/noentry` showed +7.4% (p = 0.004, n = 10) here, against +0.5% in the
#    task-8 comparison, with the hot-path code unchanged in between. The focused re-check (30 samples per side) gives
#    read +1.8% (p = 0.337) and write -3.4% (p = 0.249): the 7.4% was session noise (the baseline row itself moved from 105.9 ns to 113.8 ns
#    between sessions on this shared box).
#  * What the controls cost when they are ON (new binary only, n = 3 or 5, so indicative):
#      wrapper, per 16 KiB call:  noentry ~106 ns, entry (tracking, no limiter) ~119-128 ns serial and 140-170 ns with two cores on one entry,
#      a never-waiting ceiling ~345-540 ns, a never-waiting fair limiter plus a user speed ~1.07-1.17 us (the blocked-time brackets).
#      One door iteration moves 1 MiB per stream through the 16 KiB relay buffer = 64 calls per stream, ~21-24 ms per 16-stream iteration, so even
#      1.1 us per call is 2-3% of CPU at the door; the door rows with the controls on are within 0-6% of the tracked rows (noise +-3-20%) except one
#      conns=1 ee fair row (+26%, n = 3 on a row whose spread is +-21%), which is not repeated elsewhere. BenchmarkFairTick (once a second per fair
#      secret): 8.8 us at 16 entries, 254 us at 512, 2.5 ms at 4,096 entries (1.0 MiB and 5 allocations per tick at 4,096).
#  * Honest limit: door-row noise on this shared box is +-3% to +-24% per row, so the door A/B alone cannot certify "within 2%"; the plan's bar
#    (no significant regression above 2-3% at p < 0.05) is met on every row after the re-check, and the cost of the controls is bounded by the
#    wrapper numbers above.
#
