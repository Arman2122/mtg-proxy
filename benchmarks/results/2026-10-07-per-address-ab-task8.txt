# Per-address governance, Task 8: the counting conn's per-address step. Same-session A/B, 2026-10-07
#
# old = commit 4024026 production (before any per-address code on the data path) with the NEW
#       mtglib/door_bench_test.go copied in (the file compiles against both trees); its own
#       counting_conn_bench_test.go (noentry rows only).
# new = commit b3c5a38 (feat/client-governance; the later commit aced5dc touches only the idle sweep).
# Both: GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go test -c, run on 5.75.199.10 (2 vCPU Skylake, no SHA-NI),
#       from /root/mtg-bench, load 0.1 at the start (3 other tenants logged in).
# Protocol: 10 iterations, old and new ALTERNATED inside one session with the order swapped every
#       iteration (old,new / new,old / ...), `-test.cpu 2 -test.benchtime 1s`, TIME_WAIT < 200 between runs:
#         wrapper rows  -test.bench '^BenchmarkCountingConn(Parallel)?$/^(read|write)$/^noentry$'
#         door rows     -test.bench '^BenchmarkDoorBulk$'   (9 rows without and 9 with `/tracked`, i.e. track-client-ips ON,
#                                                             the panel's configuration; in the old binary that means "tracking, no entry")
#       then, new binary only and informational, the wrapper rows WITH an entry and no limiter (the panel's case at wrapper level),
#       -test.count 3 (benchstat cannot give an interval from 3 samples).
# Tool: benchstat (golang.org/x/perf), default settings, alpha 0.05.
#
# READ THIS BEFORE THE NUMBERS
#  * No row is slower in the new binary. 17 of 18 door rows and 4 of 4 wrapper rows show no difference (p > 0.05);
#    the one row below p = 0.05 (plain/conns=16/addr=shared/tracked, p = 0.035) is FASTER in the new binary (-3.3%),
#    which with 18 rows compared is what chance alone produces about once.
#  * The door rows are noisy (+-3% to +-24% per row on the shared box), so this A/B cannot by itself certify "no more than 2%";
#    what bounds the cost is the wrapper measurement: with an entry present and no limiter a call costs about
#    +14 ns (serial: 106 -> 120 ns) and about +75 ns when both cores hammer ONE shared entry (parallel: ~104 -> ~178 ns). A 1 MiB door
#    chunk through the 16 KiB relay buffer is 64 calls, so even the shared-entry worst case is ~1,000 calls x 75 ns = ~77 us per
#    ~21 ms door iteration, about 0.4%; the door rows are consistent with that (shared/tracked: ee +0.3%, dd -0.7%, plain -3.3%, all within noise).
#  * noentry (a stream with no entry: tracking off and no per-address control) is the old code plus one atomic load: 105.3 ns vs 106.2 ns
#    geomean (+0.9%, no row below p = 0.05; the closest, parallel/write, p = 0.052 at +3.7% with +-6-7% noise).
#
